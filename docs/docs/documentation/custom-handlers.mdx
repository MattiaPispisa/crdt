# Custom handlers

`crdt_lf` ships nine handlers (text, Fugue text, list, Fugue list, movable
list, map, register, OR-set, OR-map), but the library is not closed over
that list. A `Handler<T>` is an abstract class with a small set of extension
points, and a handler you write yourself plugs into the same document,
transaction system and sync path as the built-in ones.

## Extension points

A custom handler overrides:

- `id` and `operationFactory` — required: how the handler is addressed and
  how its operations are decoded.
- `getSnapshotState` — required: the state as bytes, seeded back through
  `lastSnapshot`.
- `handlerType` — for a handler that must survive dart2js minification (see
  the [cross-cutting gotcha](/docs/documentation) about `runtimeType`).
- `incrementCachedState` — to advance the cached state by one operation
  instead of replaying the whole history on every read.
- `stateIsOrderIndependent` — only when the state is the same whatever order
  causally ready operations arrive in.
- `compound` — to collapse consecutive operations inside a transaction into
  fewer changes.

The four conventional operation kinds (`insert`, `delete`, `update`, `move`)
are ready to use as `insertType`, `deleteType`, `updateType` and `moveType`.
A handler that needs a fifth semantics declares its own instead of reusing
one of those names:

```dart
late final OperationType incrementType =
    OperationType.custom(this, kind: 4, name: 'increment');
```

## `OperationType.custom`

```dart
factory OperationType.custom(
  Handler<dynamic> handler, {
  required int kind,
  required String name,
  bool stamped = false,
})
```

- `kind` is scoped to the **handler type**, not global — two unrelated
  handlers can both use kind `4` for two unrelated meanings, because the
  envelope always carries which handler type it addresses first. Values
  `0`-`3` are the four conventional kinds and are best left alone so tooling
  can label them without knowing the handler; `4` up to `OperationType.maxKind`
  (`127`) are free. The ceiling is `127`, not `255`, because bit 7 of the
  kind byte is reserved by the envelope, which uses it to signal that a
  stamp follows.
- `name` labels the kind in `toPayload` and debug output. It carries no
  meaning on the wire — only `kind` is written there.
- `stamped: true` turns on last-writer-wins conflict resolution for that
  kind, via an `OperationStamp` (`hlc` + `peerId`) the document mints and
  the envelope carries. `OperationType.wellKnownName(kind)` returns the
  name of a conventional kind, or `null` past those four — a kind's meaning
  depends on the handler type in front of it, so a total `kind -> name`
  function isn't expressible for custom kinds.

A change carrying a kind this build doesn't recognize for that handler type
throws `UnknownOperationKindException` instead of being silently dropped —
that's the protocol guard `crdt_lf` 4.0.0 added, and it's why a factory
never returns `null`.

## A worked example: a PN-counter

A PN-counter converges by summing every peer's contributed delta. It needs
exactly one operation kind of its own, `increment`, and no conflict
resolution: addition doesn't care what order the deltas arrive in, so
`stateIsOrderIndependent` is `true`.

```dart
class PNCounterHandler extends Handler<int> {
  PNCounterHandler(super.doc, this._id, {super.handlerType});

  /// The binary kind of an increment, the first value past the four
  /// conventional ones.
  static const int incrementKind = 4;

  final String _id;

  @override
  String get id => _id;

  /// The operation type this handler owns.
  late final OperationType incrementType = OperationType.custom(
    this,
    kind: incrementKind,
    name: 'increment',
  );

  @override
  late final OperationFactory operationFactory = _fromBytes;

  Operation _fromBytes(OperationEnvelope env, Uint8List body) {
    if (env.kind == incrementKind) {
      return PNCounterIncrementOperation.fromBodyBytes(this, body);
    }

    throw UnknownOperationKindException(
      handlerType: env.handlerType,
      handlerId: env.handlerId,
      kind: env.kind,
    );
  }

  /// Adds [by] to the counter.
  void increment([int by = 1]) {
    doc.registerOperation(
      PNCounterIncrementOperation(id: id, type: incrementType, delta: by),
    );
  }

  /// Subtracts [by] from the counter.
  void decrement([int by = 1]) => increment(-by);

  /// The sum of every delta this document has seen.
  int get value {
    final cached = cachedState;
    if (cached != null) return cached;

    var total = _initialValue();
    for (final operation in operations()) {
      if (operation is PNCounterIncrementOperation) {
        total += operation.delta;
      }
    }
    updateCachedState(total);
    return total;
  }

  @override
  bool get stateIsOrderIndependent => true;

  @override
  int? incrementCachedState({
    required Operation operation,
    required int state,
    DeltaSink<Object?>? sink,
  }) {
    if (operation is PNCounterIncrementOperation) return state + operation.delta;
    return state;
  }

  @override
  Uint8List getSnapshotState() {
    final out = BytesBuilder(copy: false);
    _writeSigned(value, out);
    return out.toBytes();
  }

  int _initialValue() {
    final snapshot = lastSnapshot();
    if (snapshot == null || snapshot.isEmpty) return 0;
    return _readSigned(snapshot, 0);
  }
}
```

The operation itself is a plain `Operation` subclass. Its body is just the
delta — the sign as one byte, the magnitude as a `UVarint` (`UVarint`
refuses negative numbers, and a counter has to move both ways):

```dart
class PNCounterIncrementOperation extends Operation {
  PNCounterIncrementOperation({
    required super.id,
    required super.type,
    required this.delta,
  });

  factory PNCounterIncrementOperation.fromBodyBytes(
    PNCounterHandler handler,
    Uint8List body,
  ) {
    return PNCounterIncrementOperation(
      id: handler.id,
      type: handler.incrementType,
      delta: _readSigned(body, 0),
    );
  }

  final int delta;

  @override
  Uint8List toBodyBytes() {
    final out = BytesBuilder(copy: false);
    _writeSigned(delta, out);
    return out.toBytes();
  }
}
```

Using it looks exactly like any built-in handler:

```dart
final doc = CRDTDocument(peerId: PeerId.generate());
final votes = PNCounterHandler(doc, 'votes')
  ..increment(3)
  ..decrement();
print(votes.value); // 2
```

This is the actual handler `crdt_lf` uses in its own test suite to prove the
custom-kind extension point works end to end — it lives at
[`test/helpers/pn_counter_handler.dart`](https://github.com/MattiaPispisa/crdt/tree/main/packages/crdt_lf/test/helpers/pn_counter_handler.dart)
today, not as a published handler. Publishing a real PN-counter as part of
the package surface is tracked separately, by
[issue #126](https://github.com/MattiaPispisa/crdt/issues/126).
